## Overview
- 25 tasks across 4 phases, including 4 checkpoints; 8 tasks parallelizable `[P]`. Single-file layout.
- Each phase follows the matching phase in `plan.md`. Dependencies after each task are prerequisites; `[P]` marks disjoint sibling work once those prerequisites are satisfied.
- Paths marked **new** are proposed files whose parent structure was checked; **existing** paths were verified in the repository. No implementation files are created by this task list.
- Deliverable: `/admin/analitica` with Resumen, Cuentas registradas, Eventos y conversiones, and Pendientes de seguimiento; Spanish content and responsive detail views.
- Preserve user decisions: authentication deferred; advertising later; active/legacy/excluded/unclassified inventory; useful verified Meta fallback accepted when quantitative website reports are unavailable. No provider-setting writes or deployment is included.
- `outputs/analytics-preview.html` is illustrative visual reference only; its numbers, identifiers and verification states must never populate live records or count as evidence.

## Dependencies and evidence gates
- Phase 1 produces live evidence and operational decisions. T1.C cannot pass on mocks or documentation alone. Missing account access/owners/hosting blocks that checkpoint, not fixture-backed development.
- T2.1–T2.6 and fixture-only T3.1–T3.7 may proceed while T1.C remains open, using clearly synthetic inputs and the provisional policy in the plan. They remain a preview; live production resource selection and capability claims require T1.C.
- T2.C requires local preview/contract evidence, T3.C requires T1.C and T2.C plus integrated reporting checks, and T4.C requires all previous checkpoints and live reconciliation/host evidence.
- Before writing implementation code, read the relevant installed Next.js guides for the chosen route, server-only and caching APIs. Reuse existing Node test conventions. No authentication design is added to this prerequisite.
- Credentials are resolved outside versioned evidence/manifests. Operational records may store approved non-secret resource IDs and safe aggregate evidence, never tokens, visitor data or provider error bodies.
