# Plan: Site-wide analytics for Camino Legal
> Status: implemented locally; production verification pending · Slug: site-expansion-analytics · Spec: ./spec.md · 2026-10-23

## Approach
Use one consent-aware measurement runtime and the existing GA4, Meta, and website email integrations. Keep navigation and forms responsible for semantic events, with shared ownership of route identity, sanitization, bounded buffering, and provider dispatch. Email transport produces operational outcomes regardless of marketing consent; accepted website submissions produce one browser-owned GA4 conversion and a deduplicated Meta browser/server outcome. Preserve normal page behavior and the current trademark animation. (FR1–FR28, TR1–TR13)

## Components affected
1. **Measurement contracts and registry** — canonical event types, eleven-route/seven-page-type registry, five services, action/content identities, payload allowlists, and privacy-safe provider mappings. Expand the catalog's item patterns against rendered controls; unused legacy components are excluded. (FR2–FR8, FR16, FR19, FR25, TR2, TR5–TR7, TR11)
2. **Consent state and preferences** — authoritative in-memory state, existing persisted preference, grant/revoke notifications, server-visible consent evidence, and a small reusable “Preferencias de cookies” entry in the legal/privacy surface so revocation is possible after the banner disappears. No new consent questionnaire. (FR21–FR24, TR9, TR13)
3. **Measurement runtime and provider adapters** — eligibility checks, bounded queue, per-destination readiness, dispatch ownership, deduplication guards, and safe diagnostics. Replace direct component calls to provider globals. (FR1, FR14–FR16, FR21–FR24, FR27, TR1–TR4, TR9, TR13)
4. **Shared route/visibility tracking** — root-layout client coordinator replaces homepage-only section ownership; canonical navigation identity, section/form/quote impressions, scroll milestones, and actual trademark-step visibility. (FR1–FR2, FR5, FR17–FR18, FR20, FR28, TR5, TR8, TR10)
5. **Rendered navigation and content surfaces** — navbar, footer, sticky bar, home/service/about/FAQ/process/reviews interactions receive semantic identities and one primary action classification. Legal links and official references remain distinguishable from contact intent. (FR3–FR4, FR16, FR19, TR6, TR10)
6. **Quotation experience and attribution** — current quotation instance, actual service/configuration snapshots, both disclosures, evaluation lifecycle, and explicit service context carried into evaluation. Reuse current calculator output instead of copying pricing formulas. (FR5–FR8, FR25, TR5–TR7, TR11)
7. **Contact and evaluation form lifecycle** — shared measurement semantics with form-specific validation, visibility, starts, submission attempts, safe failures, and accepted outcomes; replace page-lifetime UUID/success guards. Evaluation remains email-only. (FR9–FR11, FR14–FR15, FR28, TR2–TR4, TR11)
8. **Email operation and restricted Meta handoff** — existing server action remains the email entry point; recipient-aware acceptance, structured operational metrics, accepted-outcome receipt, and a separate post-success server action for consent-checked Meta delivery. (FR12–FR15, FR21, FR23, FR27, TR2–TR4, TR12–TR13)
9. **Reporting, migration, and verification** — core dimensions/key-event mapping, operational log queries/export, historical cutover notes, and a complete route/action/consent test matrix. (FR26, TR1, TR4, TR6, TR11–TR12)

## Data model changes

### Canonical browser records
- Keep the catalog envelope: schema version, event/outcome identity and occurrence time, page-view identity, canonical route/type, service/context, registered source/action/content/destination, and consent status. Runtime validation rejects unregistered properties rather than forwarding arbitrary objects. (FR2–FR3, FR25, TR2, TR5–TR6)
- One navigation identity per committed route arrival; provider readiness and rerenders do not create identities. Back/forward arrivals do; quotation selector-only changes update context without manufacturing another canonical page. A same-route “Inicio” scroll action records its action without another page view. (FR1, TR5)
- `form_instance_id` lasts until form remount/new logical form instance; `attempt_id` changes for each deliberate submit, including validation failures. Use bounded `attempt_number` for deliberate retries, retaining the originating instance. Keep logical submission identity separate from transport-attempt identity: the one automatic unknown-outcome retry creates a second transport attempt under the same submission. `outcome_event_id` identifies one accepted attempt and remains stable across provider representations and repeated result rendering. (FR9–FR15, FR28, TR4, TR11)
- `quote_id` belongs to the mounted quotation workspace, surviving local service/configuration changes; a newly mounted workspace gets a new identity. Snapshot fields reuse live displayed calculator values; custom proposals retain null money and trademark-only controls. (FR5–FR7, TR7)
- No person entity, analytics database, unique-client deduplication, SMTP idempotency store, or permanent visitor identifier is introduced. Two deliberate accepted attempts can create two leads/messages; repeating one analytics delivery cannot. (FR15, TR4, TR11–TR12)

### Consent and temporary state
- Consent snapshot: status, monotonically changing local revision/opaque version, and changed-at time. In-memory state is authoritative during a visit even when storage fails; persisted existing choice only initializes a new visit. Broadcast/storage notifications synchronize available tabs; unsupported persistence never turns unknown into granted. (FR21–FR24, TR13)
- A session cookie mirrors consent status/version for server actions, signed by a server-only secret; it contains no identity/profile. Only grant/revoke acknowledgement enables a server marketing handoff. Browser measurement may follow the current in-memory grant independently of cookie support. Cookie inability disables server marketing safely, not email submission. (FR21–FR23, TR2, TR13)
- Eligible pending events live in memory only: maximum 50 events, maximum age 30 seconds; coalesce duplicate page/section identities and drop oldest pending records on overflow. Dispatch-state markers are per event and destination, not shared blindly between GA4 and Meta. Revocation clears pending records and the current eligibility epoch. (FR24, TR9)
- Short-lived conversion receipt: an opaque authenticated-encrypted envelope containing accepted outcome identity, occurrence time, form kind, safe context, collection-consent version, expiry, and server-normalized email/optional-phone matching hashes, trusted canonical website source, and a bounded request user agent confined to this restricted lane. Encrypt and authenticate the entire envelope with a dedicated server-only key; a merely signed readable token must not contain matching hashes. Keep the receipt and decrypted matching lane out of generic event payloads/logs. Only the server creates this receipt after intended-recipient acceptance with eligible collection consent; arbitrary client IDs cannot mint accepted outcomes. Receipt lifetime is five minutes, not a visitor/session retention period. (FR14–FR15, FR21–FR23, TR2–TR4, TR13)

### Operational email records
- `email_attempted` / `email_result`: event identity, timestamp, actual transport attempt identity, form kind, bounded attempt number, consent state at collection, stage/outcome, nonnegative integer duration in milliseconds, and allowlisted error category. (FR12–FR13, TR12)
- Transport outcomes: intended recipient accepted; recipient rejected; known transport failure; uncertain acceptance (`unknown`). A resolved send operation with no confirmed intended-recipient acceptance is not success. Do not log the transport response object, addresses, message IDs containing external data, exception text, or message content. (FR13–FR14, TR2, TR12)
- Use content-free structured application logs through a small operational sink contract; no new datastore. Export/query availability and retention depend on the actual deployment log service and are a launch gate, not assumed present. (FR26, TR12)

## Interfaces & contracts

### Browser measurement boundary
- **Record event:** registered event name plus its typed payload and current page/service context → accepted, ineligible, invalid, buffered, or unavailable result. This is observational; callers never branch business behavior on analytics availability. (FR3–FR11, FR16–FR20, FR27–FR28, TR6)
- **Consent transition:** granted/denied plus current revision → immediate local transition and optional persisted/server acknowledgement. All provider entry points check current consent at collection and dispatch, including existing loaded globals. A transition notification fires for every state change, not only grants. (FR21–FR24, TR13)
- **Route transition:** canonical route, validated quotation service context, and committed arrival identity → one pending page-view record and reset page-specific impression/milestone guards. Current visible targets begin fresh qualification after mid-page grant. (FR1–FR2, FR17–FR18, FR20, FR22, FR28)
- **Provider adapters:** canonical record → a minimal event-specific allowlisted projection, not the entire envelope. Each projection must fit the destination’s supported event-name/parameter-name lengths, parameter counts, value types, and value lengths, verified against current official limits before activation. Canonical null quotation amounts remain null internally; omit unsupported null provider properties rather than reporting zero. Event/outcome IDs remain technical correlation fields, never registered reporting dimensions. Readiness flushes existing identities instead of generating events. No generic forwarding of DOM attributes, link URLs, errors, or form values. (FR24, FR27, TR2, TR6, TR9)

### Event delivery ownership

| Canonical group | GA4 owner | Meta owner | Operational sink |
|---|---|---|---|
| `page_view` | Browser coordinator, manual only | Browser coordinator, one `PageView` per same eligible navigation | None |
| Core navigation/service/quotation/forms and secondary engagement | Browser adapter using canonical catalog names | No duplicate custom mirroring by default | None |
| WhatsApp/email/quotation email intent | Browser canonical channel event | Browser `Contact` with safe channel/source distinction; no `Lead` | None |
| `lead_submitted` | Browser accepted-result callback only | Browser `Lead` plus restricted server `Lead`, same outcome identity | Not a second lead counter |
| `email_attempted`, `email_result` | No marketing export by default | None | Server operation only |

- GA4 `lead_submitted` is the sole proposed lead key event; superseded `contact_form_submit` must not also count the same acceptance. No server Measurement Protocol path or generic GA4 event-ID deduplication assumption. Browser guards prevent repeated success emission; avoid retrying an ambiguous GA4 send because the provider may already have accepted it. (FR14–FR15, FR26, TR1, TR4)
- GA4 manual page ownership requires disabling initial automatic page views and automatic history page views: application `send_page_view=false` is necessary but does not disable the separate Enhanced Measurement browser-history setting; the account toggle must also be off. Disable overlapping enhanced form, outbound-link, and scroll measurements; retain only reviewed measurements whose payloads and counting do not conflict. Meta initialization no longer owns its own extra page view. Verify account settings as well as application behavior. (FR1, FR16, FR20, TR2, TR10)
- Before initialization and every route/event update, set provider page location to the known site origin plus canonical path, safe fixed title, and sanitized referrer; represent valid `servicio` as a field, not a raw query. Allowlisted campaign categories may be retained only after consent. Unknown paths/URLs become a safe unknown identity, never a raw echo. (FR2, FR25, TR2, TR5, TR11)
- Meta automatic events/advanced matching must not independently inspect form contents or send uncontrolled URLs. Automatic payload inspection is a verification gate. Custom event fields or a custom event-source URL do not prove the Pixel’s implicit document-location/referrer fields are safe. If supported configuration cannot establish safe initialization and subsequent event payloads, suppress the browser Pixel on that surface and allow only a separately eligible sanitized CAPI handoff; otherwise keep that provider disabled. Do not monkeypatch browser location/referrer or change browser history to disguise unsafe fields. (FR21, FR27, TR2–TR3)
- Register only low-cardinality reporting dimensions: page type/path, service/context, action/source, channel, form kind, bounded control/content IDs and outcomes. Correlation IDs stay for technical reconciliation and distinct-instance calculation, not custom report dimensions. (FR26, TR6, TR11)

### Website form and email contract
- **Submission input:** existing business fields plus declared form kind, attempt identity/number, safe explicit service/quotation context, and collection-consent status/version. Validate all measurement metadata independently; missing/malformed optional metadata never prevents a valid business submission. Contact validation includes its required phone; evaluation validation does not invent a phone requirement. (FR10–FR15, FR25, TR2–TR4)
- **Submission result:** status `validation_failed`, `accepted`, `recipient_rejected`, `transport_failure`, or `unknown`; safe user-facing message, attempt identity, safe validation categories, and accepted outcome identity only on confirmed acceptance. Issue a restricted conversion receipt only when collection consent was granted and acknowledged; never return contact data in generic outcome metadata. (FR11–FR15, FR21, TR2–TR4, TR13)
- **Email transport boundary:** valid message → attempted record → intended-recipient acceptance/rejection/failure/uncertainty → terminal metric and user result. Use bounded transport connection/greeting/socket deadlines; an unknown outcome triggers exactly one automatic retry with a new transport-attempt identity under the same logical submission. Preserve the first unknown result; stop after the second attempt if still unknown and expose it for operational review. Confirmed rejection/failure does not trigger this automatic retry. Possible duplicate messages are explicitly accepted. Exact deployment-compatible deadlines are verified before release. (FR12–FR13, FR27, TR12–TR13)
- **Restricted conversion handoff:** after an accepted result, the browser first rechecks collection/current consent and revision. Only then may it invoke a separate existing-framework server action with the authenticated-encrypted accepted receipt and current consent version. The server authenticates/decrypts the receipt and verifies expiry, accepted outcome, allowed form/context, and a granted matching-version consent cookie from that fresh request before dispatch. It derives matching hashes and outcome identity only from the authenticated receipt, never arbitrary client assertions of success or separately submitted client hashes/IDs. No new public analytics HTTP route is needed. (FR14–FR15, FR21–FR23, TR2–TR4, TR13)
- Normalize/hash email and optional phone inside the restricted server receipt/Meta lane, using only the business data accepted by the email action; evaluation uses email without a phone gate. Keep hashes, matching integrity, access tokens, request bodies, and provider error responses out of generic events and logs. The same accepted outcome identity goes to Meta browser/server; final supported deduplication mapping is verified in Events Manager. Replaying a valid receipt retains the same outcome identity; it cannot authorize another SMTP send. (FR14–FR15, TR2–TR4)
- The same-origin restricted CAPI handoff depends on current consent and an authentic accepted receipt, independently of Pixel script readiness or availability; a blocked Pixel must not block an otherwise eligible server handoff. Browser tab closure may still prevent the callback, with no delivery guarantee. Meta dispatch is bounded to a short request deadline (proposed two seconds), never inside the SMTP success decision, and has no durable retry queue. Missing configuration, blocked callbacks, expired receipts, consent changes, or provider failure can lose marketing attribution while the email remains accepted. No retry of SMTP follows from these failures. (FR27, TR1, TR13)

### Consent timing and revocation boundary
- Defer server marketing until a fresh post-SMTP handoff, rather than calling Meta from the original long-running email request. Revoking during SMTP prevents the browser handoff; granting after an unconsented submission cannot mint a historical eligible lead. A grant that occurred before runtime readiness is captured by the shared consent snapshot and bounded eligible buffer. (FR21–FR24, TR9, TR13)
- Revocation immediately blocks new local marketing dispatch, cancels pending provider work where possible, clears queued events/attribution, and updates the consent cookie before any future server handoff. Serialize cookie grant/revoke updates so an older grant acknowledgement cannot overwrite a newer denial in that tab. Handoffs with mismatched receipt/current revisions are discarded. (FR23–FR24, TR9, TR13)
- The server can observe consent in its latest incoming request, not subsequent browser actions. A marketing request already dispatched before revocation cannot be unsent; a revocation racing after a fresh handoff request was issued may not be observable to that request. Do not claim instantaneous cross-request/global revocation without durable shared consent state. Verification asserts no new dispatch after revocation is known to the local runtime or handoff request; document in-flight limits explicitly. (FR21–FR23, TR13)
- Browser provider SDKs already loaded cannot be unloaded reliably; revoke their consent/disable mechanisms where supported and block every application adapter entry point. Automatic provider traffic is tested; uncontainable provider behavior blocks activation. Reconsent begins a fresh eligibility epoch without replay. (FR21–FR24, TR2, TR13)

### Visibility, deliberate actions, and attribution
- One shared observer lifecycle applies 50% visibility for one continuous second in a visible document. Oversized sections use registered representative targets; short targets must correspond to actual content, not a distant heading or decorative arrow. Pause/reset qualification on hidden tabs, page changes, consent loss, or target exit. (FR5, FR17–FR18, FR28, TR8)
- Once-per-page guards include form instance/quote identity where relevant. A post-grant currently visible target starts qualification from zero. One event per scroll threshold; no raw scroll payloads or frame callbacks for analytics. (FR17–FR18, FR20, FR22, FR28, TR8–TR10)
- Explicit handlers identify actual manual control origins: review arrows/dots/swipes, process tabs/next/previous, FAQ open/close, both quote-cost and payment-schedule disclosures. Automatic carousel rotation, scroll-driven process changes, native initialization, and the trademark arrow never masquerade as user action. (FR6, FR18–FR19, TR10)
- Carry safe explicit service context from service CTA to quotation and into evaluation. Generic contact may use only an explicit supplied context or a consented in-memory session referral; preserve `unspecified` otherwise. Keep displayed calculator default distinct from deliberate interest. (FR25, TR5, TR11)
- Optional menu/theme/legal utility events are a separate last-phase engagement tier; required navigation/contact links within those surfaces remain core. Do not measure denied-consent button choices through marketing to prove consent behavior. (FR3, FR16, FR21, TR2)

## Implementation phases
1. **Contracts and privacy foundation** — registry/types, consent memory/revision transitions, server evidence contract, safe payload boundaries, and fake provider/transport seams. Done when invalid/PII payload and denied-consent tests pass without changing functional flows. (FR2, FR21–FR25, FR27, TR2–TR6, TR9, TR11–TR13)
2. **Route ownership and core surfaces** — one coordinator for eleven URLs, provider initialization/readiness, manual page-view ownership, desktop/mobile navigation and all rendered business CTAs/service choices. Done when coverage inventory and consent/reload/history tests reconcile. (FR1–FR4, FR16, TR1–TR2, TR5–TR6, TR9–TR10)
3. **Quotation and form lifecycles** — current-value quotation snapshots, both disclosures, evaluation open/close, form exposure/start/attempt/validation/failure, and safe service attribution. Done when all five services, controls, and both forms match catalog semantics. (FR5–FR11, FR25, FR28, TR4–TR8, TR10–TR11)
4. **Email outcomes and conversion integrity** — intended-recipient transport classification, operational records, accepted results, browser-owned GA4 lead, and separate consent-rechecked Meta handoff. Done when fake transport success/failure/uncertainty, duplicates, retries, email-only evaluation, and revocation-during-SMTP tests pass. (FR12–FR15, FR21, FR23, FR27, TR1–TR4, TR12–TR13)
5. **Bounded engagement and reporting** — section/step visibility, scroll milestones, manual FAQ/process/reviews, business funnel/report definitions, and operational log query/export evidence. Optional utility events may follow without blocking core readiness. (FR17–FR20, FR26, FR28, TR6, TR8–TR12)
6. **Cutover verification and release readiness** — audit live provider settings with owner, historical event/key-event mapping, complete acceptance matrix, retention approvals, and controlled environment verification. Done when every AC has evidence and launch gates are resolved; deployment remains a separate user action. (FR1–FR28, TR1–TR13)

## Dependencies & integrations
- Existing Next 16.2.3/React 19.2.4 application, Nodemailer transport, GA4 identifiers, Meta Pixel identifier/server secret, and SMTP credentials. No new runtime package is required for event typing, observers, bounded buffering, structured logs, or authenticated encryption/signing. Built-in cryptography requires a dedicated server-only receipt-encryption/consent-signing secret. (TR1–TR4, TR8–TR9, TR13)
- Keep cookies inside server actions rather than reading request cookies from every root layout/page, preserving current static route behavior. Follow installed Next async-cookie and server-action guidance; put any root client search-parameter observer behind the required Suspense boundary for prerendered routes. No assumptions from older Next releases. (FR1, FR27)
- Existing native Node tests import the quotation domain and exercise actual pricing/email-draft behavior; extend that testing style for pure contracts and adapters. Browser verification needs an available supported browser automation environment; installation is not assumed. (TR6–TR10)
- Production provider administrator and deployment-log access are dependencies for configuration audit, debugging evidence, operational exports, and retention. The deployment platform/log sink is not established by current repository inspection. (FR26, TR12)

## Reviewed risk decisions
- Consent: recheck at dispatch and after email processing; clear pending marketing events on revocation. Already-issued requests cannot be recalled.
- Conversion gaps: server operational outcomes are authoritative for confirmed submissions; GA4/Meta provide consent-limited attribution. Unknown outcomes remain separate from confirmed acceptance.
- Email uncertainty: allow exactly one automatic retry after an unknown outcome, accepting possible duplicate messages. Preserve separate transport outcomes under one logical submission and count at most one canonical lead. Stop and flag a second unknown for operational review.
- Payload safety: one tracking owner per event, allowlisted fields, and outgoing-payload inspection before launch.
- Operational access: demonstrate submission/attempt lookup and totals export; approve access and retention before launch.
- Historical continuity: mark cutover, document changed definitions, and establish a fresh baseline for changed metrics.

## Risks & tradeoffs
- **Consent race and SDK autonomy** — fresh post-success handoff and authenticated-encrypted receipts add a dedicated secret dependency and narrow stale-consent exposure but cannot revoke already-issued network traffic; validate and document the bounded guarantee instead of introducing a consent database. (FR21–FR24, TR13)
- **Browser-owned GA4 lead loss** — tab closure, blockers, or missing configuration can prevent conversion delivery after accepted mail; operational acceptance remains the authoritative website-send count. Avoid uncertain retries that could duplicate GA4 events. (FR14–FR15, FR27, TR4)
- **Transport ambiguity** — timeouts and recipient-level rejection can differ from resolved promises; unknown stays visible and triggers one automatic SMTP retry; possible duplicate messages are accepted in preference to a missed email. Both transport attempts share one logical submission and at most one canonical lead. A second unknown stops retrying and remains available for review. A deliberate user resubmission is a new logical submission. (FR12–FR15, TR4, TR12)
- **Automatic PII/duplicate collection** — provider settings and implicit URLs can defeat clean custom payloads; block activation until intercepted/live payload inspection and automatic-measurement ownership agree. (FR1, FR21, TR2, TR5)
- **Operational reporting availability** — structured logs alone are not a dashboard or durable guaranteed delivery; require a demonstrated deployment query/export before claiming complete production email reporting. (FR26, TR12)
- **Historical comparability and attribution gaps** — old contact-only totals and new evaluation coverage differ; publish cutover mapping, denominator definitions, unknown-context buckets, and consent-limited reporting. (FR25–FR26, TR4, TR11)
### Alternatives considered
- Server Measurement Protocol plus browser GA4 leads — rejected because it adds identifier/secret handling and duplicate-outcome risk without a requirement for a second GA4 transport. (FR14–FR15, TR1, TR4)
- Meta dispatch inside the original SMTP action — rejected because its consent snapshot can be stale by the time a long send completes. (FR21, FR23, TR13)
- New analytics endpoint/database/durable worker — rejected for this scope; existing server actions and log delivery suffice, with explicit best-effort marketing limits. (FR26–FR27, TR1, TR12–TR13)
- Automatic provider measurement as primary ownership — rejected because canonical route/context, duplicate avoidance, and URL/content exclusion require explicit review and control. (FR1–FR2, TR2, TR5)

## Test strategy
- **AC1:** Browser network interception across all eleven URLs, reload/internal/back/forward navigation, quotation query changes, same-route navigation, delayed readiness, and rerenders. Assert one eligible page identity per actual arrival per provider and sanitized context. (FR1–FR2, TR5)
- **AC2:** Table-driven rendered action inventory at desktop/mobile widths; exercise visible links and verify stable event/source/destination classification, including navbar contact variants/footer/legal/sticky. Ignore unused legacy components. (FR3, TR6)
- **AC3:** Domain/adapter tests for five directory selections and quotation service changes; browser tests distinguish default initialization from deliberate selection. (FR4–FR6, TR10)
- **AC4:** Extend existing native quotation tests to compare snapshots directly with calculator outputs at classes 1/10, rules on/off, payments 1/2/3, all custom services, and both disclosure toggles; no copied tracking price table. (FR5–FR7, TR7)
- **AC5:** Form integration/browser tests for dialog open/close paths, first interaction, native and server validation, accepted/rejected/uncertain sends, failed attempt retry, and repeated success rendering. Validate safe categories, not raw messages. (FR8–FR11, TR2)
- **AC6:** Fake SMTP returns intended-recipient accepted/rejected, throws known failures, and simulates ambiguous timeout; assert attempt/result records and absence for validation-only failures in every consent state. Verify unknown→accepted, unknown→unknown, and unknown→failure sequences: exactly two transport attempts, preserved individual outcomes, no third automatic attempt, and one logical submission/at most one lead. No live email sends. (FR12–FR13, TR12)
- **AC7:** Fake adapters count one GA4 success and one Meta outcome identity across browser/server representations per accepted attempt; repeated rendering/delivery retains identity, deliberate retry increments attempt identity/number. Evaluation succeeds without phone. (FR14–FR15, TR3–TR4)
- **AC8:** Browser activation interception proves mailto/WhatsApp/social/official-reference behavior and correct intent classification without ever claiming send/purchase or firing a lead. (FR7, FR16)
- **AC9:** Controlled visibility/clock tests plus browser scrolling prove one-second/50% exposure, hidden-tab reset, post-grant qualification, step content versus arrow progress, reduced motion, manual reviews/process selection versus automation. (FR17–FR19, TR8, TR10)
- **AC10:** Scroll geometry tests cover threshold crossings/revisits, page reset, no-scroll pages, and no per-tick event stream. (FR20, TR8, TR10)
- **AC11:** Intercept all GA4/Meta browser/server destinations with unknown/denied consent, mid-page grant, failed storage, slow script load, and grant-before-listener readiness. Assert zero prohibited traffic and no pre-grant replay. (FR21–FR22, TR13)
- **AC12:** Revoke with loaded adapters, queued records, pending SMTP, and pending consent acknowledgements; test fresh handoff mismatch/expiry and no future dispatch after locally observed denial. Distinguish already-issued network requests from new ones in evidence. (FR21–FR24, TR9, TR13)
- **AC13:** Fake clock/adapter readiness tests enforce 50 records/30 seconds/coalescing/overflow; browser tests block each provider and omit configuration. Analytics failures never alter accepted email or trigger transport again. (FR24, FR27, TR9)
- **AC14:** Inspect payloads, URLs, referrers, titles, diagnostics, receipts' restricted boundary, and operational records with synthetic PII canaries; test crafted query/campaign/form/error values. Verify generic contact unspecified attribution. (FR25, TR2–TR3, TR5, TR11–TR12)
- **AC15:** Reconcile synthetic journey events and structured email logs into catalog funnels/rates: view-to-start denominators, distinct interacted `quote_id`, intents versus accepted attempts, unknown outcomes, and one canonical conversion. Check low-cardinality reporting dimensions. (FR26, TR4, TR11–TR12)
- **AC16:** Complete matrix spans seven page types/eleven URLs/five services, responsive controls, consent, navigation history, failures/retries, duplicate delivery, and outages. Run native tests, lint, TypeScript, production build, and focused browser smoke checks; inspect controlled live-provider diagnostics only after owner/configuration approval. (FR1–FR28, TR1–TR13)
- **AC17:** Contact/evaluation visible-form tests assert one `form_view` per form-instance/page-view, hidden/unmounted exclusion, and a fresh view for a reopened evaluation form instance without counting rerenders. (FR28, TR8)

## Assumptions
- This work targets the current versioned `.claude/analytics/site-expansion` specification and catalog; legacy analytics documents stay intact. Implementation is not authorized by producing this plan. (TR1, TR6)
- Owner access, retention, and legacy-event continuity remain nonblocking for design, but mandatory production launch gates. No account state, active key-event registration, deploy platform, or existing operational query capability is assumed. (FR26, TR1, TR12)
- Existing provider identifiers and SMTP remain intended integrations; a dedicated receipt-encryption/consent-signing secret can be configured server-side before restricted handoff activation. Missing secret disables CAPI safely and leaves email/user feedback operational. Restricted website handoffs also require a configured trusted HTTPS `META_WEBSITE_ORIGIN` and a bounded request user agent; neither belongs in generic events or logs. (FR27, TR1, TR13)
- Five-minute receipt lifetime and proposed two-second Meta deadline are local reliability/security design defaults; transport deadlines must fit deployment limits. They do not select production analytics/log retention. (FR27, TR12–TR13)
- The in-flight revocation boundary is an explicit distributed-system limit. Stronger instantaneous cross-request revocation would require revisiting the no-shared-state design; this plan does not silently promise it. (FR21–FR23, TR13)

## Open decisions
- **Launch gate — ownership:** Name the person approving/reporting GA4 key events, Meta mapping and deduplication evidence, enhanced-measurement settings, provider projection limits, supported safe SDK initialization/canonical-URL handling, and production verification. Unsafe implicit location/referrer traffic blocks provider activation; custom property overrides alone are not evidence of safety. Existing Meta endpoint/version must be checked against supported official documentation before release; current source version is not endorsed by this plan. (FR14, FR26, TR1, TR4)
- **Launch gate — retention and operational destination:** Approve analytics/log retention and demonstrate how structured operational logs are queried/exported on the actual host; do not claim an email dashboard before that exists. (FR26, TR11–TR12)
- **Launch gate — historical continuity:** Approve old-to-new names/key-event cutover and document the evaluation-coverage change; no dual firing of legacy and canonical lead events. (FR14–FR15, FR26, TR4, TR6)
